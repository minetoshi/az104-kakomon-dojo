AZ-104 12か月無料ハンズオン 完全版

「無料枠で実際に触れるところは実機」「少しでも課金の読みづらいところはマニュアル」に分けた、AZ-104用の実戦ハンズオンです。各Labに 目的 → Portal手順 → CLI/Bicep → 確認 → 試験ポイント → 後片付け → 理解チェック を入れています。

先に読んでください。 Azure の無料サービスは「対象SKU・月間無料量・12か月の有効期間」まで無料です。対象外SKUや付随リソースを選ぶと課金される場合があります。この教材では、Azure Portal の Cost Management + Billing ＞ Free services にあなたのアカウントで表示される条件を最優先にします。

↑上へLab 0　課金事故防止・共通準備

実機所要 15〜20分合格に直結: Cost / RG / Tag / Budget

目的: 以降のハンズオンを1つのRGへ集約し、無料枠残量と削除対象を見失わない状態を作ります。

0-1. 無料枠を確認

  1. Azure Portalへサインイン。
  2. 上部検索欄で Cost Management + Billing を検索。
  3. 使用している課金アカウント/サブスクリプションを選択。
  4. Free services を開き、12か月無料の残量と終了日を確認。
  5. VMを使う予定なら、対象VM SKUがあなたの画面に表示されることを確認。表示されないSKUはこの教材では作りません。
期待結果: 「12 months」「Free」「Remaining」等の表示で、対象サービス・残量・終了日を確認できる。

0-2. 専用リソースグループ

Portal ＞ Resource groups ＞ Create
Subscription自分の12か月無料対象サブスクリプション
Resource grouprg-az104-free-lab
RegionJapan East など、自分が使うリージョン
  1. Resource groups → Create。
  2. 名前を rg-az104-free-lab にする。
  3. 作成後、RGの Tags を開く。
  4. Purpose=AZ104、DeleteAfter=今日の日付 を追加。

0-3. Budget

  1. Cost Management → Budgets → Add。
  2. できるだけ低い金額で予算を作り、通知先メールを自分に設定。
  3. しきい値 50% / 80% / 100% などを設定。
重要: Budget は課金を止めません。しきい値超過時に通知するだけです。「自動停止装置」と思わないこと。
理解チェック

Q: Budgetを100円にすれば100円でAzureが止まる？
A: いいえ。Budgetは通知/管理用で、リソースや消費を自動停止しません。

↑上へLab 1　Resource Group / Tag / Lock / RBAC

実機所要 25分公式: ID & Governance

目的: AZ-104で頻出の「分類」「削除保護」「権限」をPortal上で切り分けます。

1-1. Tag

  1. rg-az104-free-lab → Tags。
  2. Department=IT を追加。
  3. サブスクリプションの Tags 画面から Department=IT で絞り込めることを確認。
試験: Tagはメタデータ。Tagだけでは削除や変更を止められません。

1-2. Resource Lock

  1. RG → Locks → Add。
  2. Name: lock-delete、Lock type: Delete。
  3. RG内に任意の無料リソースがあれば削除を試す。なくてもRGの削除ボタンまで進み、ロックが阻止することを確認。
  4. Lockを削除する。
CanNotDelete: 読み取り・変更はできるが削除不可。
ReadOnly: 読み取りだけ。管理プレーンの更新操作も止まり、影響が大きい。

1-3. RBAC

  1. RG → Access control (IAM) → Role assignments。
  2. Add role assignment を押し、Reader / Contributor / Tag Contributor の説明を読む。
  3. 実際に別ユーザーがいなければ、割り当て確定は不要。Role → Members → Review + assign の流れを確認する。
  4. Check access で自分の現在のアクセスを確認。
覚え方: Reader=読むだけ / Contributor=リソース変更 / Owner=変更+アクセス管理 / Tag Contributor=タグ管理に特化。
理解チェック

Q1: VMを削除させたくないが設定変更は許可したい。ReadOnlyとCanNotDeleteのどちら？
A: CanNotDelete。

Q2: ユーザーにタグだけ変更させたい。Contributorより適したロールは？
A: Tag Contributor。

↑上へLab 2　Bicep 読解・build・what-if

ローカル中心所要 45分公式: ARM/Bicep

目的: 「Bicepの単語を知っている」から「既存Bicepを読んで修正できる」へ進めます。

2-1. 最小Bicep

param location string = resourceGroup().location param prefix string = 'az104' resource vnet 'Microsoft.Network/virtualNetworks@2024-05-01' = { name: '${prefix}-vnet' location: location properties: { addressSpace: { addressPrefixes: [ '10.50.0.0/16' ] } subnets: [ { name: 'subnet-app' properties: { addressPrefix: '10.50.1.0/24' } } ] } } output vnetId string = vnet.id
  1. Azure Cloud Shell またはローカルAzure CLIを開く。
  2. main.bicep として保存。
  3. az bicep build --file main.bicep を実行。
  4. 生成されるARM JSONを開き、Bicepの param/resource/output がどのように変換されたか確認。
az bicep build --file main.bicep

2-2. for / if / existing / module を読む

param names array = [ 'st01' 'st02' ] resource dummy 'Microsoft.Storage/storageAccounts@2023-05-01' = [for name in names: if (length(name) > 0) { name: '${uniqueString(resourceGroup().id)}${name}' location: resourceGroup().location sku: { name: 'Standard_LRS' } kind: 'StorageV2' }]
  • for = 反復。
  • if = 条件付きデプロイ。
  • existing = 新規作成せず既存リソース参照。
  • module = 別Bicepファイルを再利用。
0円方針: buildまではローカル処理です。what-if / deployは対象リソースによって課金が絡むので、無料範囲で使うVNet程度に限定してください。
理解チェック

Q: 既存Storage accountを再作成せず参照するキーワードは？
A: existing。

↑上へLab 3　VNet / Subnet / NSG / ASG / UDR

実機所要 45〜60分公式: Virtual Networking

目的: IP設計、NSG、ルート、Peeringの関係を「画面」で覚えます。NVAやVPN Gatewayは作りません。

3-1. VNet A

Virtual networks ＞ Create
Namevnet-az104-a
Address space10.10.0.0/16
Subnetsnet-app / 10.10.1.0/24

3-2. VNet B

Virtual networks ＞ Create
Namevnet-az104-b
Address space10.20.0.0/16
Subnetsnet-back / 10.20.1.0/24
試験: PeeringするVNetのアドレス空間は重複不可。10.10.0.0/16 と 10.10.1.0/24 は重複しています。

3-3. NSG

  1. Network security groups → Create → nsg-az104-app。
  2. Inbound security rulesを開く。
  3. TCP 443 Allowルールを作る。Priorityは例として100。
  4. 同じポートのDenyルールをPriority200で作り、「小さいpriorityが先」の意味を確認。
  5. 最終的には不要なルールを削除し、安全な状態に戻す。
  6. NSG → Subnets → vnet-az104-a/snet-app に関連付け。

3-4. ASG

  1. Application security groups → Create → asg-web。
  2. VM/NICがなくても、NSG ruleのSource/DestinationでASGを選べることを確認。
試験: ASGはNICの論理グループ。IPアドレスを直接並べずに「Web群」「App群」のようにNSGを記述できます。

3-5. UDR

Route tables ＞ rt-az104 ＞ Routes ＞ Add
Route namedefault-to-nva
DestinationIP Addresses
Destination IP/CIDR0.0.0.0/0
Next hop typeVirtual appliance
Next hop address10.10.1.4（NVAは作らない）

設定画面を確認したら、通信断を避けるためルートを保存せずに戻るか、保存した場合はすぐ削除します。

3-6. Peering

  1. vnet-az104-a → Peerings → Add。
  2. Remote VNetにvnet-az104-bを指定。
  3. 双方向の「Allow virtual network access」を確認。
  4. 作成後、PeeringsがConnectedになることを確認。
  5. 大量データ転送はしない。理解確認後にPeeringを削除してよい。
試験: Peeringは非推移的。A-B、B-Cを作ってもA-Cが自動でつながるわけではありません。
理解チェック

Q1: 特定VM群をNSGの宛先にまとめたい。何を使う？
A: ASG。

Q2: 全通信をNVAへ。UDRの宛先とNext hopは？
A: 0.0.0.0/0、Virtual appliance。

↑上へLab 4　Blob / SAS / Versioning / Soft Delete / Lifecycle

12か月無料所要 60分公式: Storage

目的: StorageをAZ-104で最も出やすい「アクセス制御」と「データ保護」に分けて体験します。

4-1. Storage account作成

Storage accounts ＞ Create
Resource grouprg-az104-free-lab
Name世界で一意な名前（例: staz104xxxx）
PerformanceStandard
RedundancyLocally-redundant storage (LRS)
Hierarchical namespaceOff（今回）
無料枠ガード: Hot LRSの小さいBlobだけを使います。ZRS/GRSや大容量データはこのLabでは不要。

4-2. Container / Blob

  1. Storage account → Data storage ＞ Containers → + Container。
  2. Name: lab、Anonymous access level: Private。
  3. PCで version1.txt を作り、中身を「v1」にする。
  4. Upload。
  5. 同名ファイルを「v2」に変えて後で上書きするため、いったん次のVersioningへ。

4-3. Versioning と Soft Delete

  1. Storage account → Data management ＞ Data protection。
  2. Enable versioning for blobs をON。
  3. Enable soft delete for blobs をON。保持期間は学習用に短めの値を選択。
  4. 保存。
  5. version1.txt の中身を「v2」に変更して同名上書き。
  6. Blobの Versions から旧版が残っていることを確認。
  7. Blobを削除し、Deleted blobs表示から復元動作を確認。
Versioning: 書き換え時の旧版を残す。
Soft delete: 削除したデータを保持期間内に復元。
両方ON: 削除時の挙動が少し変わるので、Version一覧も確認する。

4-4. Lifecycle Management

  1. Data management ＞ Lifecycle management → Add rule。
  2. Rule name: move-to-cool。
  3. Scope: Base blobs。
  4. 条件: Last modified 30 days ago。
  5. Action: Move to cool storage。
  6. 設定内容を確認。実際に30日待つ必要はありません。
試験: Lifecycleは「自動でtier移動/削除」。VersioningやSoft deleteの代わりではありません。

4-5. SAS 3種類

Service SAS: 1つのStorage service内のリソースへ委任。Stored access policyと関連付け可能。
Account SAS: 複数Storage serviceやサービスレベル操作まで委任可能。Stored access policy不可。
User delegation SAS: Microsoft Entra資格情報で署名。Microsoft推奨。Stored access policy不可。
  1. Container lab を開く。
  2. PortalでSAS作成画面を開き、権限(Read/Listなど)、Start/Expiry、HTTPS onlyを確認。
  3. User delegation SASを作る場合、アカウントに必要なRBAC権限があることを確認。
  4. 有効期限を短くし、SAS URLをブラウザで試す。
  5. 学習後、生成したSASは保存せず破棄。
重要: Stored access policyと結び付けるのはService SAS。User delegation SAS / Account SASにはStored access policyを使いません。
理解チェック

Q1: Entraで署名するSASは？
A: User delegation SAS。

Q2: 発行済みSASの期限をサーバー側ポリシーで変更したい。どの組合せ？
A: Service SAS + Stored access policy。

↑上へLab 5　Azure Files / Snapshot / Soft Delete

12か月無料所要 35分公式: Storage

5-1. File share

  1. 同じStorage account → Data storage ＞ File shares。
  2. + File share。
  3. Name: share-lab。
  4. Tierは無料枠表示と一致する標準/LRS側を選び、極小容量だけ使う。
  5. 数KBのテキストファイルを1個Upload。

5-2. Snapshot

  1. File shareを開く。
  2. Snapshots → Add snapshot。
  3. 元ファイルを書き換える。
  4. Snapshotから旧状態を確認。

5-3. Soft Delete

  1. Storage account → File shares → Soft delete 設定を確認。
  2. 保持期間を確認。
  3. Share削除→Deleted sharesから復元、という流れを確認。実際に試す場合はデータを極小にする。
試験: SMBはTCP 445。Share snapshotは共有のポイントインタイムコピー。Soft deleteは削除されたFile shareを保持期間中に復元。

↑上へLab 7　無料対象VM / Managed Disk / Redeploy

12か月無料所要 50〜70分公式: Compute
このLabだけは開始前に必ずFree servicesを確認。 VM SKUは、あなたのPortalで12か月無料と明示されるものだけを選んでください。2026年9月の公式料金ページでは B2ts v2 / B2pts v2 / B2ats v2 が各750時間/月と案内されていますが、リージョン在庫やアカウント表示を優先します。

7-1. VM作成

Virtual machines ＞ Create ＞ Azure virtual machine
Resource grouprg-az104-free-lab
Namevm-az104-free
Region無料SKUが選べるリージョン
ImageUbuntu LTS等（有償OSイメージは避ける）
SizeFree services画面に出る対象Bシリーズ
Public inbound portsNone
Public IPNone
OS disk無料枠対象P6 64GBを意識
課金回避: Public IP、Bastion、Load Balancer、Premiumな追加機能を付けません。VMサイズを「よく似た別SKU」に変えないでください。

7-2. Run commandでOSを確認

  1. VM → Operations ＞ Run command。
  2. LinuxならRunShellScriptを選ぶ。
  3. uname -a、df -h 等の読み取り系コマンドを実行。
uname -a df -h lsblk

Public IPを付けずに、PortalからゲストOS情報を確認できることを体験します。

7-3. Data disk

  1. VM → Disks → Create and attach a new disk。
  2. 無料枠の2本目として使う場合、P6 64GBを超えないようにする。
  3. 保存。
  4. Run commandで lsblk を再実行し、新しいdiskを確認。
  5. VM → Disks からData diskをDetach。
  6. 再度Attach。
試験: Data diskはOS diskとは別。対応VM/SKUなら停止せずdetachできるケースがあります。設問条件を読む。

7-4. Redeploy

  1. VM → Help ＞ Redeploy + reapply（Portalの位置は変更されることがあります）。
  2. 説明を読み、「別Azure hostへ移動する」意味を確認。
  3. 実行する場合、短時間で完了後すぐdeallocate。
区別: Redeploy=ホスト移動 / Resize=VM SKU変更 / Reimage=OSイメージ再適用 / Move=RG・Subscription・Region移動。

7-5. Deallocate と削除

  1. 学習が終わったら Stop ではなくPortalで Stop (deallocate) 状態を確認。
  2. 最終的にはRGからVM、NIC、Diskを削除。
  3. OS diskの「Delete with VM」設定にかかわらず、削除後にRG一覧を目視して残骸がないか確認。
後片付け: VMを消してもdiskやNICが残ることがあります。RGのResources一覧でゼロになるまで確認してください。
理解チェック

Q: VMがホスト障害っぽい。OSやdiskを維持したまま別ホストへ移したい。何を使う？
A: Redeploy。

↑上へLab 8　Azure Container Registry / RBAC・ABAC

Free services表示がある場合所要 30〜40分公式: Containers
開始条件: Free services画面でACR無料枠が表示されること。表示されない場合は マニュアルのみ に切り替えてください。

8-1. Registry作成

  1. Container registries → Create。
  2. RG: rg-az104-free-lab。
  3. Registry name: 世界で一意。
  4. SKU: Free services画面に明示された対象。
  5. 作成。

8-2. 権限モード

  1. Registry → Properties。
  2. Role assignment permissions mode を確認。
  3. RBAC Registry Permissionsなら AcrPull / AcrPush を確認。
  4. RBAC Registry + ABAC Repository Permissionsなら Container Registry Repository Reader / Writer を確認。
重要: ABAC対応registryではlegacyのAcrPull/AcrPush/AcrDeleteを使いません。問題文に権限モードがあれば最優先で読む。

8-3. IAM

  1. Access control (IAM) → Add role assignment。
  2. 「pullだけ」「push+pull」の最小権限候補を検索。
  3. 実際の割当先がなければ確定せず、ロール説明を読むところまででよい。

↑上へLab 9　App Service Free の基本

Free tierのみ所要 30分公式: Compute / App Service
境界: Free tierでWeb Appの基本だけ触ります。Deployment slots、Azure Monitor Autoscale、VNet Integration、Private EndpointなどStandard/Premium側の機能は実機にせず マニュアルで確認します。

9-1. Web App作成

  1. App Services → Create → Web App。
  2. Publish: Code。
  3. Runtime: 任意の無料で使えるruntime。
  4. Pricing plan: Free F1 が表示される場合のみ選択。
  5. 作成。

9-2. 基本設定

  1. Web App → Settings / Configuration。
  2. HTTPS Only、Minimum TLS versionの設定場所を確認。
  3. Scale upでFree/Basic/Standard/Premiumの機能差を見る。変更はしない。
  4. Deployment slotsを開き、「Free tierでは使えない/制限がある」ことを画面上で確認。
試験: CPU/MemoryのAzure Monitor AutoscaleはStandard以上。Deployment slotも上位tierが必要。Free F1で「できない機能」を見ること自体が勉強になります。
